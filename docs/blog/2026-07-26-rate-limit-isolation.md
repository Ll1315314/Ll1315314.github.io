# 前台搜索为什么会「卡」——一次下游额度隔离的排查

> 我一度想靠加并发解决前台搜索的卡顿问题。排查到最后，发现瓶颈根本不在并发度上，而在**共享的下游 API 额度**上。这次排查让我彻底分清了两件事：并行度解决的是「能同时跑多少」，资源隔离解决的是「谁能拿到有限的外部资源」。

## 一、先摆清楚牌桌上有几张牌

排查性能问题，最忌讳的是还没搞清楚系统结构就开始「优化」。第一步永远是把牌桌上的牌摊开来看。这套系统里有三个核心组件，各司其职，彼此嵌套：

| 组件 | 本质 | 关键参数 | 职责 |
| --- | --- | --- | --- |
| `xhsMonitorExecutor` | **线程池** | core=2, max=4, queue=10 | 让后台监控任务异步/并行跑 |
| `XhsKeywordSearchQueue` | **单线程队列** | 1 线程 + 阻塞队列 | 前台搜索请求排队、串行逐个处理 |
| `OneApiRequestQueue` | **单线程队列（每 Key 一个）** | 1 线程 + 请求间 `delayMs` 延迟 | 串行调用第三方接口、天然限流 |

注意三个关键事实，后面所有推理都建立在这上面：

1. **监控线程池故意开得很小。** `core=2`、`max=4`，这本身就是一种「别让后台占太多资源」的限流设计。不是疏忽，是刻意为之——设计者的直觉是对的，只是没做到位；
2. **前台关键词搜索是单线程串行的。** 一次只处理一个关键词，每处理一个就要调若干次第三方 API。它从一开始就不是并行系统；
3. **所有对第三方接口的调用，最终都汇进按 Key 的单线程限流队列。** 这些队列是串行的，请求之间有固定延迟，目的就是防频控。不管上层怎么折腾并发，最终都会在某个 Key 的队列上汇合、排队、串行化。

这三层结构像漏斗一样，把上层的并发一层层收束，最终挤压到下游的一个狭窄出口上。

## 二、现象：前台搜索时快时慢，还和后台"撞点"

系统里有两个功能都要调同一个付费第三方接口：

| 功能 | 触发方式 | 行为特征 | 延迟容忍度 |
| --- | --- | --- | --- |
| 后台监控 | 定时触发，批量探测一批帖子 | 周期性、可预期、量大 | 高 |
| 前台搜索 | 运营手动触发关键词分析 | 突发性、交互式 | 低（要求秒回） |

前台搜索的用户体验很诡异：**有时候秒回，有时候转半天，甚至给人一种「失效了」的感觉。**

更让人困惑的是，「卡」的时机非常有规律——**总是和后台定时任务到点重合。** 运营一到整点就反馈「搜索又卡了」，而其他时间段基本正常。

这种「规律性卡顿」其实已经是一个很强的信号了。随机卡顿可能是 GC、网络抖动、锁竞争；但**和时间点强相关的卡顿，几乎一定和某个定时触发的任务有关。**

## 三、弯路：直觉让你加并发，但并发不是瓶颈

看到「卡」，第一反应几乎都是——**加并发**。当时我也顺着这个方向想：

- 是不是监控线程池太小了？把 `core=2 / max=4` 调大点？
- 是不是前台该多开几个线程同时搜？

但只要冷静三秒钟就会发现不对：

- **前台搜索本来就是单线程串行的。** 它慢，不是因为「线程不够并行」——它压根就没在并行。一个关键词处理完才处理下一个，线程数对它毫无影响。给它 100 个线程，它也只用 1 个；
- **监控线程池就算调大，和前台的响应速度也八竿子打不着。** 它们是两条完全不同的处理链路，监控池管的是后台任务的并行度，和前台搜索的响应路径没有直接关系。

> 就像你开了十条收费车道，但前方只有一个收费亭开着。你开一百条车道，车也还是在排队。**瓶颈在收费亭，不在车道数。**

加线程没用，说明瓶颈不在并发能力上——**任务确实起来了，但它们都在等同一个东西。**

## 四、根因：共享的下游额度被"饿死"了

顺着「都在等什么」往下追，真相浮出来了：

> **后台监控和前台搜索，最终都把请求汇进了同一批第三方接口 Key 的限流队列。**

前台搜索那条单线程，每处理一个关键词都要发若干次 API 调用；这些调用和监控的探测请求，排进了同一批 `oneapi-{key}` 队列。而这些队列是串行的、每次请求之间还有固定延迟——为的就是不触发平台频控。

于是发生了这样的事：

```text
后台定时任务到点触发
        │  一次性灌入一大批探测请求
        ▼
┌─────────────────────────────────────────────────────┐
│   共享的 OneAPI Key 队列（串行 + 请求间固定延迟）      │
│                                                     │
│  [监控①][监控②][监控③] … [监控ₙ]                       │ ← 被后台占满
│  [前台①][前台②] ……（排在后面干等）                     │ ← 前台的 API 调用
│                                                     │
└─────────────────────────────────────────────────────┘
        │
        ▼
    第三方接口
```

后台任务到点后一口气把共享队列填满。前台搜索虽然有自己的处理线程，但它发出的 API 调用只能排在监控请求后面等额度。

**「卡」的本质不是计算不够快，而是下游额度被后台饿死了。**

这时候你给任何一层加线程，都只是制造更多「假忙」的等待者——看着并发很高，实际都堵在同一个串行限流队列后面。线程池越大，越多线程一起 `wait()`，上下文切换开销反而更大。监控线程池从 4 调到 10，只不过是多制造了 6 个一起排队的线程而已。

## 五、解法:资源隔离,而不是加线程

方向一旦对了,解法就清晰且简单:**不是加线程,是把额度分开。**

给监控配一份独立的速率预算(独立限流器),让它只花自己那份,不再和前台挤同一批 Key 队列:

```text
监控任务  ──►  监控专用限流器（默认 10 次/分钟）
                │
                └──►  第三方接口（总限流仍生效，但两路互不干扰）

前台搜索  ──►  前台专用限流器（较高速率，如 50 次/分钟）
                │
                └──►  第三方接口
```

关键设计点：

| 设计决策 | 原因 |
| --- | --- |
| 监控限速刻意压低（默认 10/分钟） | 后台批量行为，用户不实时等待，延迟容忍度高 |
| 前台留更高额度 | 交互式操作，直接挂钩用户体验 |
| 物理隔离（各自维护令牌桶） | 互不知晓对方存在，后台再忙也抢不走前台的额度 |
| 监控侧加独立限流器 | 只对监控限速、完全不碰前台；同一批 Key 下也不再挤占前台额度 |

改完上线后，后台定时任务再怎么批量灌请求，前台的关键词搜索都稳定秒回。前台那条单线程终于不用在共享队列后面「陪跑」了。

这里有一个值得注意的细节：**我选择在监控侧加限流器，而不是在前台侧。** 原因是——监控是「侵扰者」，是它占满了队列导致前台饿死。治标要治本，把「肇事者」管住，比给「受害者」开绿色通道更符合直觉，也更容易维护。

## 六、一个必须厘清的概念:并行度 ≠ 资源配额

这次排查最大的收获,是把两个经常被混为一谈的概念彻底分开了。很多性能问题的误诊,根源就在于这两个概念没有被正确区分。

| 概念 | 解决什么问题 | 典型手段 | 适用场景 |
| --- | --- | --- | --- |
| **并行度** | 任务能不能同时执行 | 线程池、协程池、连接池 | CPU / IO 密集型计算 |
| **资源配额** | 有限的外部资源怎么公平分配 | 限流器、配额系统、租户隔离 | 第三方 API、数据库连接、带宽 |

线程池解决的是「我能同时发起多少请求」。限流器解决的是「有限的外部额度怎么分」。

当瓶颈在共享的外部资源上时，加线程只会制造更多等待者——你让更多人一起排队，并不会让队伍前进得更快。相反，过多的等待线程还会带来额外的上下文切换开销和内存占用。

> **一个更形象的类比：** 想象一家只有 4 个充电桩的充电站——线程池 = 停车场里有多少辆车在等；限流器 = 充电桩的分配规则（谁先充、充多久、每天最多充几次）。如果你发现「车等太久」，解决方案不是「让更多车进来等」（加大线程池），而是给不同类型的车分配不同的桩或时段（资源隔离）。
>
> 更进一步：如果你发现「救护车等得太久」，你不会说「那就多派几辆救护车同时等吧」，而是会说「给救护车开一个专门的优先通道」。**优先级和隔离，比单纯的并发度更有意义。**

## 七、顺手清掉的几个"慢性毒药"

借这次重构，我把监控模块里一批「单看不大、合起来要命」的隐患一起修了。它们不会立刻炸，但会让系统在长期高频运行中逐渐失控。

**1. 评论增量误判 → 无效重拉**

原逻辑：每次检查帖子有没有新评论，是通过数据库里该帖子的评论行数来判断的。

问题：评论可能被删除、被折叠、被审核过滤，导致 DB 行数和平台显示的 `comment_count` 不一致。结果是——系统以为有新评论，全量重拉，实际上什么都没变。

修复：直接比对平台返回的 `comment_count` 字段。这是平台认定的「公开可见评论数」，是判断增量的最权威来源。

> **本质问题：** 用派生数据（DB 行数）去推断原始事实，而不是用源头数据本身。这就像通过「垃圾桶里的果皮数量」来判断「家里有多少人吃了水果」——中间环节太多，误差不可避免。
>
> **延伸思考：** 在分布式系统中有一个通用原则——**单一事实来源（Single Source of Truth）**。如果某个事实在多个地方都有「副本」，你必须以那个最权威的来源为准，而不是挑一个方便的来用。

**2. 失败不推进游标 → 每分钟空转**

原逻辑：定时任务每次拉取一批帖子，成功后更新 `last_crawl_at` 游标；失败后不更新，下次继续从上次的位置拉。

问题：如果某一批中有一个帖子拉取失败（比如接口超时），游标不前进，下一分钟任务再次触发，又从头拉同一批——然后再次失败，形成永久性空转循环。

修复：失败也推进游标。记录失败原因，但让任务继续往前走；失败的帖子单独进入重试队列，不影响整体进度。

> **本质问题：** 把「单条失败」的异常处理，错误地耦合到了「整体进度」的控制逻辑上。这就像快递员因为有一户人家不在家，就把整条街的配送都推迟到明天——显然不合理。
>
> **延伸思考：** 在批处理系统中，要区分**瞬态失败**（网络超时、限流，应重试）和**永久失败**（资源不存在、权限不足，应跳过并记录）。但无论哪种失败，都不应该阻塞整体进度。

**3. 手动触发不走锁 → 和定时任务打架**

原逻辑：定时任务有分布式锁（Redis Lock），但手动触发的接口没有。运营点一下「立即分析」，可能同时触发多个实例。

问题：手动触发 + 定时任务同时运行 = 双倍请求打到第三方接口 = 更容易触发限流 = 恶性循环。

修复：手动和定时统一走同一套锁机制——同一个入口、同一把锁；进程内再加一层 `AtomicBoolean` 做去重，双重保险。

> **本质问题：** 同一个业务逻辑，有两套并发控制策略（一套有锁，一套没锁），必然出现竞态条件。这就像同一条路既有红绿灯又有交警，而且他们之间不沟通——迟早出事故。
>
> **延伸思考：** 分布式锁的正确使用方式是「**一处加锁，处处遵守**」。一旦某个业务路径使用了分布式锁，所有访问同一资源的路径都必须经过同一把锁，否则锁就形同虚设。

## 八、这些"小坑"的共同特征

回头看这三个问题，它们有一个共同点：**都不是「bug」，而是「设计上的隐性债务」。**

它们不会在上线第一天暴露，因为：数据量小时，`comment_count` 和 DB 行数的差异不明显；失败概率低时，游标不前进的问题不频繁；并发度低时，锁缺失的后果不严重。

但随着系统运行时间变长、数据量变多、触发频率变高，这些问题会从「偶尔的小异常」演变成「系统稳定性的慢性杀手」。

修这些坑的意义，不是让系统「跑得更快」，而是让系统「在长期高频运行中不失控」。这也是为什么很多系统「上线时好好的，跑半年就崩了」——不是代码变差了，是隐性债务在累积利息。

## 九、一个通用的排查框架

这次经历让我沉淀了一个排查「卡顿」问题的思考框架，适用于任何依赖外部资源的系统：

```text
第 1 步  确认"卡"在哪里
        ├── 线程 RUNNABLE？          → 计算瓶颈（CPU / 算法）
        ├── 线程 WAITING/TIMED_WAIT？ → 同步等待（IO / 锁 / 条件变量）
        └── 线程 BLOCKED？           → 锁竞争

第 2 步  如果是等待，在等什么
        ├── 等 CPU / 内存 / GC？→ 扩容 / JVM 调优
        ├── 等锁？             → 锁粒度优化 / 减少持锁时间
        └── 等外部资源？       → 进入第 3 步

第 3 步  外部资源是否共享
        ├── 是 → 是否存在资源争抢？
        │        ├── 有 → 资源隔离（限流配额拆分 / Key 分离）
        │        └── 无 → 优化调用模式（批处理 / 缓存 / 合并请求）
        └── 否 → 检查资源本身的健康状态（下游服务是否变慢）

第 4 步  验证假设
        ├── 加监控指标（队列长度、等待时间、吞吐量、成功率）
        ├── 做对照实验（关闭后台任务，观察前台响应）
        ├── 打日志（记录每个请求在哪个阶段花了多长时间）
        └── 确认根因后再动手改
```

这个框架的核心思想是：**从现象到根因，每一步都要有证据支撑，而不是靠直觉「我觉得应该是……」。**

## 十、一句话总结

当系统依赖有限的外部资源时，「加线程」是最诱人但也最无效的优化手段。真正需要做的，是**承认资源的稀缺性，然后通过隔离和配额来公平地分配它。**

**线程池让你「跑得快」，资源隔离让你「跑得稳」。** 在依赖第三方 API 的系统中，后者往往比前者重要得多。

下次遇到「明明加了并发还是卡」的情况，先别急着调线程数——看看是不是有人在共享队列后面排队等额度。

如果你也在做涉及第三方 API 的系统，或者对「如何设计合理的限流与隔离策略」有更多想法，欢迎交流。特别是在多租户场景下的配额设计和优先级调度，这里面还有很多值得深挖的细节。
