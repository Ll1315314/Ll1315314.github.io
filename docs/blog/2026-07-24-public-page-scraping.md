# 用公开页 `INITIAL_STATE` 替代付费接口做数据快照

> 一次把第三方接口成本打到 0 的降本实践——以及一次被证据支撑的「放弃」。

## 背景：钱花在哪了

我们有一个「内容数据快照」的需求：定期采集一批笔记的互动数字（点赞 / 评论 / 收藏 / 转发），用于后续分析。原方案走的是付费的第三方接口，一个月一笔不小的开销，而且大量冷内容的探测其实是无效的。

目标很朴素：**在不牺牲数据可用性的前提下，把这笔接口成本压下去。**

## 关键发现：数字本来就印在公开页里

快照真正需要的只是几个互动数字，而这些数字**在服务端渲染时就已经写进了公开笔记页的 HTML** 里——具体是页面里的 `window.__INITIAL_STATE__` 这个 JSON。

这意味着：

- **不需要登录**，不调用任何登录态接口；
- 对平台而言，这就是一次普通的公开页访问，行为上和真人点开一篇笔记没有区别；
- 于是它天然是 **0 账号、0 风控、0 成本**。

Java 侧的移植逻辑非常直接：

```java
// 伪代码，示意流程
String html = httpGet(publicNoteUrl);              // 1. GET 公开页
String json = extractInitialState(html);           // 2. 正则抠出 __INITIAL_STATE__
InteractInfo info = parseInteractInfo(json);        // 3. 解析 interactInfo
// info.likedCount / commentCount / collectedCount / sharedCount
```

在真实链接上实测，稳定拿到了点赞、评论、收藏、分享四个数字。分享长链里带的 token 我实测一个多月都不过期，所以连刷新机制都不用做。

## 诚实的局限

- **播放量（views）拿不到**——但付费接口现在也拿不到（平台限制），所以这条不算损失。
- **公开页方案是脆的**：平台一改版，解析就可能失效。

对第二点，我的态度是把它设计成**「成本优化」而不是「强保证」**：

1. 抓不到就**自动回退**到付费接口，保证数据不断供；
2. 解析层对结构做容错，字段拿不到就走回退，而不是抛异常整批失败；
3. 它只承担「要数字」的快照，强依赖登录态的能力本来就没押在它上面。

换句话说——**优化失效时，优雅降级回原来的付费基线，不会造成功能性事故。**

## 那正文为什么不也自建？——一次被证据支撑的放弃

评论正文走的是**登录态的懒加载接口**，公开页拿不到。我确实认真尝试过自建替代（httpx + 逆向签名的开源方案），但评论接口稳定返回一个「账号异常」错误码。我没有停在「大概被风控了」，而是做了一套控制变量的排除法：

- **排除验证码**：抓原始响应，确认返回的不是滑块 / 验证页，就是纯粹的异常码；
- **排除 IP**：响应头证实我确实走的是住宅 IP，不是机房 IP；
- **排除账号**：新号、老号、无痕环境、养过的号，全测，全异常；
- **排除 TLS 指纹**：用 `curl_cffi` 把 TLS/JA3 指纹伪装成真实 Chrome（**实测已生效、指纹一致**），仍然被拦。

连接层（IP、TLS/JA3）都伪装到位还是被拦，根因就只能落在**更上层的请求行为特征**：httpx 这类非浏览器客户端在请求时序、header 组合、以及缺少真实浏览器执行环境上，和真浏览器有本质差异。这意味着指纹浏览器、TLS 伪装都救不了——除非上真实浏览器自动化，而那条路又会触发**账号级**封控。

**结论：正文继续走付费接口，不再往自建投入。**

## 一点体会

做降本这件事，最有价值的产出不一定是「省了多少钱」，而是**把可行边界摸清楚**：

- IP 层、TLS 层（JA3）、应用行为层是三个独立的对抗面，要能逐层定位、逐层排除；
- 一次能被证据支撑的「不做」，能帮团队省下之后所有在死路上的投入——这和一次成功的「做」同样重要。

最终这套方案让快照与高频探测的接口成本降到了 0，正文成本只在「确实有新内容」时才发生。
