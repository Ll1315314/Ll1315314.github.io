# 别让 AI 猜「成没成单」——用真实订单做 Ground Truth

> 用关键词/大模型判断一段客服对话「有没有成交」，准确率永远打问号。直到我们把真实订单数据接进来做校验。

## 一、问题：你在让 AI 做一件它没有资格做的事

很多对话分析系统的设计，从一开始就有个隐含假设：**对话文本里包含了所有你需要知道的信息。** 于是你会看到这样的架构：

```text
对话文本 → LLM / 规则引擎 → 是否成单（✅/❌）
```

靠什么判断？关键词匹配 + 语义推测。但这套逻辑有一个致命缺陷：**聊天记录里根本不包含「是否真的下单」这个信息。**

- 买家说「我下单了」，可能只是客套、敷衍，或者真点了但没付款；
- 真正下单的买家，大量是**静默下单**——聊完之后一声不吭，直接去 App 里自己完成支付。他们在对话里留下的痕迹，和「只是随便问问」的人几乎没有区别。

结果就是：你的「是否成单」字段，**未知率一度接近 90%**。你以为自己在做数据分析，实际上是在用精美的报表包装一个巨大的问号。更隐蔽的是——即使那 10% 「已知」的部分，准确率也无从验证，因为没有 Ground Truth，你甚至不知道自己错了多少。

## 二、转折点：真值不在文本里，在数据库里

有一天我们突然意识到：**成单与否，从来就不是一个需要从对话中「推断」的信息，而是一个已经在别处被确定的事实。**

真值在订单系统里，白纸黑字，带着时间戳、金额、商品 ID、买家昵称。你不需要猜，你只需要对齐。思路一转，架构变成：

```text
对话文本  ──┐
            ├──→ 关联 → 是否成单（✅/❌，由订单数据决定）
订单数据  ──┘
```

做法很朴素：维护一份 `platform, buyer`（平台 + 买家昵称）的订单名单，用真实下单数据去覆盖 AI 的猜测。成单率的计算也从「模型输出汇总」变成纯粹的数据统计：

```text
成单率 = 聊过天 且 在订单名单里的买家数 / 聊天总买家数
```

每个买家的成单状态，不再取决于他在聊天里说了什么，而是取决于**他到底有没有付钱**。AI 的「猜」被降级为参考，真实订单成了裁判。

## 三、意外收获：看见"静默下单"的缺口

两份数据对起来之后，一个过去完全不可见的人群浮出水面：**有订单、但从没聊过天的买家**——他们是静默下单者，不咨询、不比价、不纠结，直接下单。这批人的存在，对业务分析有两个关键影响：

**1. 重新评估客服的价值。** 没有订单数据时，你会把所有成交都归因给「聊过天的买家」。但有一部分成交本来就会发生，无论有没有客服介入。静默下单者的比例，决定了「客服带来的**增量**」的真实大小——如果 30% 的成交来自静默下单，那客服的贡献就得从「0 到 100%」重新核算成「70% 到 100%」。

**2. 发现流量质量的信号。** 静默下单率高，往往意味着品牌信任度高、复购强、或商品决策成本低；反之，如果几乎没人静默下单，说明用户普遍需要大量沟通才能转化，这可能指向产品说明不足、价格偏高或信任度问题。这些都是从纯对话分析里永远看不到的信号。

## 四、反向筛选：哪些该让 AI 做，哪些不该

这件事让我对「AI 落地」有了一个更清醒的判断框架：**每一个你拥有确定性数据源的判断，都应该由那个数据源来做硬判定，而不是交给模型软推断。**

这个原则看似简单，却经常被违反——因为「用 AI 显得高级」「懒得写数据对接」。基于它，可以把对话分析里的常见任务分个类：

| 任务 | 是否有确定性真值 | 应该谁来判 |
| --- | --- | --- |
| 是否成单 | ✅ 有（订单系统） | 数据库硬判定 |
| 是否退款 | ✅ 有（售后系统） | 数据库硬判定 |
| 购买商品品类 | ✅ 有（订单明细） | 数据库硬判定 |
| 客单价区间 | ✅ 有（订单金额） | 数据库硬判定 |
| 流失原因 | ❌ 无现成真值 | LLM 推断 |
| 用户意向等级 | ❌ 无现成真值 | LLM 推断 |
| 对话摘要 | ❌ 无现成真值 | LLM 推断 |
| 用户情绪倾向 | ❌ 无现成真值 | LLM 推断 |

**AI 适合做的，是没有真值、或真值获取成本太高的判断。** 凡是数据库里已经有答案的问题，模型就不该插手——它不是在做「智能分析」，只是在「试图还原一个它本可以直接读取的事实」，而且还还原不准。

## 五、一个更通用的模式：硬判定 + 软推断的分工

把上面的思考抽象一下，会得到一个适用于很多 Agent 落地的分工框架：

```text
┌──────────────────────────────────────────────────────┐
│  硬判定层（Hard Determination）                      │
│  数据来源：数据库、日志、外部 API、传感器             │
│  特点：确定性强、可验证、成本低                       │
│  例子：是否成单、是否退款、库存是否充足、是否已登录   │
│  责任方：工程代码 + 数据库查询                        │
├──────────────────────────────────────────────────────┤
│  软推断层（Soft Inference）                          │
│  数据来源：文本、图像、语音等非结构化数据             │
│  特点：不确定性高、难验证、需要语义理解               │
│  例子：流失原因、用户意图、情感分析、摘要生成         │
│  责任方：LLM / 多模态模型                             │
└──────────────────────────────────────────────────────┘
```

成熟的 Agent 系统，往往是**硬判定在外围把关，软推断在内核做理解**。比如一个电商客服 Agent：库存、价格、订单状态走硬判定（数据库），而怎么回复、语气、意图理解走软推断（模型）。**硬判定负责「对不对」，软推断负责「怎么说」**，各司其职，互不越界。

## 六、警惕"全 AI 化"的诱惑

当前行业有一种隐性审美：**越「全 AI」的方案越容易被认为高级**。如果一个系统里还有大量规则、SQL、硬编码，似乎就显得「不够 AI」。

但这种审美是有毒的。Agent 落地的本质是**解决问题**，而不是展示模型能力。如果你的业务数据里已经有一个 100% 准确的答案，你却选择用一个 80% 准确率的模型去「预测」它，这不是技术创新，是工程上的失职。**真正的专业度，体现在你知道什么时候不该用 AI。**

## 七、一句话总结

当你的「是否成单」不再依赖模型从字里行间揣摩，而是直接来自订单表的白纸黑字时，你失去的只是一点「全 AI」的虚荣，得到的却是整个分析体系的可信度。

在 AI 落地的路上，**克制比激进更需要勇气，也更值得尊重。** 如果你也在做对话分析或 Agent 落地，欢迎交流更多关于「如何划定 AI 边界」的实践经验。
