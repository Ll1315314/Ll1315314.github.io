# 批量发布的难点不是点按钮，是记账——10 账号 × 205 条视频的排期设计

> 一个取模运算解决了排期，真正花力气的是证明它不会算错：630 行代码里藏了 12 类共 25 处主动中止。防的都是同一件事——「跑得很顺利，然后悄悄干错了事」。

## 一、题目长什么样

10 台云手机，每台挂一个账号。素材库共有 225 条视频，但前 20 条（#1~#20）已在别处发过，本次实际可用 205 条。要求：

- 每天发 1~2 轮，每轮 10 台机各发 1 条；
- **每个账号自己不能发重复的视频**；
- 一轮跑完要记住发到哪了，第二天接着往下；
- 跑满之后，每个账号都发满 205 条不重复的内容（一天 2 轮约 103 天跑完）。

手工做一轮：新建任务 → 勾 10 台机 → 切分批设置 → 传 10 个视频 → 粘 10 份文案 → 核对 → 发布。十来分钟，一天两次，连续三个多月。

一开始我以为要解决的是「点按钮太累」。写完才发现，**点按钮是最简单的部分**。

真正难的是记账：第 87 轮该给第 3 号机发哪条视频？靠人维护 Excel，错一格就是某个账号发了条重复的——而且这个错误**当场看不出来**，等发现的时候已经积累了几十轮。

## 二、把状态压成一个整数

排期规则最后写成了一行：

```js
const poolIdx = (r, d) => (r - 1 + d - 1) % pool.length
```

第 `r` 轮、第 `d` 台机，发第 `(r-1+d-1) mod N` 条视频。展开看就是个环形滑动窗口：

```text
轮 1:  机1→v21   机2→v22   机3→v23   …  机10→v30
轮 2:  机1→v22   机2→v23   机3→v24   …  机10→v31
轮 3:  机1→v23   机2→v24   机3→v25   …  机10→v32
 …
轮205:  机1→v225  机2→v21   机3→v22   …（绕回开头）
```

这一个式子同时满足了三件事：

| 要求 | 为什么成立 |
| --- | --- |
| 账号内零重复 | 机 `d` 从 `v[20+d]` 起步，环形往后走，跑满 205 轮正好各发一次 |
| 同轮 10 台内容各不相同 | 同一轮里 `d` 不同则下标必不同，不会 10 个账号同天发同一条 |
| **进度可推导** | 不需要记录「哪台机发过哪些」，只需要记住**当前第几轮** |

第三条是最大的收益。整个系统的持久化状态就是一个整数 `nextRound`。

**状态越少，能出错的地方越少。** 如果我当初老老实实建一张「设备 × 视频」的已发表，它会有 2050 行、需要考虑并发写入、需要考虑部分失败时回滚哪些行——而这些问题现在全都不存在。

文案维度上我做了个取舍：10 台共用第 `r` 条。同一天 10 个账号文案相同，但换来的是文案序列也天然不重复。素材有限时，把「不重复」的预算优先花在视频上更划算。

顺带一个小设计：`--plan` 参数会把排期打印出来给人验：

```text
  轮  1: 视频 #21~#30  文案 001.txt
  轮  2: 视频 #22~#31  文案 002.txt
       …
  轮205: 视频 #225~#29 (绕回开头)  文案 205.txt
```

**一个纯数学的规则，能在三秒内验证**——这比在代码里写十行注释管用。

## 三、公式有两个前提，而它们都会悄悄失效

`(r-1+d-1) % N` 要成立，得先保证两件事：**视频的编号固定，设备的顺序固定**。

这俩都不是自动成立的。更麻烦的是，它们失效的时候**不报错**，只是默默发重复内容。

### 前提一：目录排序会背叛你

最初的写法是 `readdirSync(dir).sort()`，编号 = 排序后的下标。

问题在于三个月后往素材库补几条新视频。如果新文件名排在中间，**整个序列往后挪一格，所有历史轮次的编号全部错位**。

解法是把编号**冻结**进一个 `video-index.json`，然后立两条规矩：

- **新增只能追加到末尾**，绝不重排；
- **发现缺失直接中止**。

第二条是关键。文件不见了，最省事的实现是跳过它继续跑——但那等于让后面所有编号往前挪一位。所以这里选择停下来，把丢失的文件名打出来，让人去恢复。

### 前提二：页面顺序也会背叛你

云机列表的顺序不由我控制。它可能因为平台改版、排序规则调整、某台机重启而变化。顺序一变，「第 3 台机」就不是原来那台了，环形窗口直接错乱——**而页面上一切正常**。

所以首轮把设备顺序记进进度文件，之后每轮比对，不一致就中止：

```js
} else if (prog.deviceOrder.join(',') !== deviceRows.join(',')) {
  console.error('\n设备顺序与首轮不一致，继续跑会破坏「每台账号不重复」的保证：')
  console.error(`  首轮: ${prog.deviceOrder.join(', ')}`)
  console.error(`  本轮: ${deviceRows.join(', ')}`)
  throw new Error('设备顺序变化，已中止')
}
```

注意报错**把首轮顺序和本轮顺序都打出来了**。只说「设备顺序变了」是没用的，人没法判断该怎么办；两行摆在一起，一眼就能看出是某台机换了位置，还是整个列表被重排。

> 这两处校验的共同点：**规则的前提要显式检查，而不是默认它成立。** 一个依赖前提的公式，如果不校验前提，它就不是「正确」，只是「暂时还没错」。

## 四、进度：整轮成功才写盘

在正常发布流程里，进度文件的写入只有一处，在整轮流程的最末尾。中途任何一步抛错，进度都停在原地。

> 注：仅在更换整批素材（`runNewCycle`）时另有一次重置写入，不属于日常发布逻辑。

所以给非技术同事的文档里可以直接写：

> **报错之后进度会不会乱？不会。** 进度是整轮跑完才记录的，中途失败不影响，直接重跑就行。

这就是把「事务」用在一个 630 行脚本上——要么整轮填好，要么当没发生过。发布这一步在事务之外，需要人工确认。

对一个每天要跑、由非技术同事操作、报错是常态的工具来说，这条比任何精细的异常处理都值钱：**用户永远只需要做一个决定——重跑。**

### 顺带：进度文件丢了怎么办

有个组合值得单独处理：**进度文件没了，但编号表还在**。

这基本只有一种解释——误删。天真的实现会当成首次运行，从第 1 轮开始，而第 1 轮的内容三个月前就发过了，10 个账号会集体重发一遍旧视频。

所以这里停下来，把后果说清楚，并要求一个显式的确认参数：

```text
进度文件 progress.json 不存在，但 video-index.json 在。
如果直接继续，会从第 1 轮重新发一遍已经发过的内容。
确认要从头开始，请执行：bash publish.sh --yes
```

**推断出用户可能犯了错时，不要替他把错误执行掉。**

## 五、当默认值比报错更危险

参数解析这段，注释本身就是理由：

```js
// 三种写法都认：--limit 2 / --limit=2 / --limit2
// 写错的参数必须报错退出，绝不能静默退回默认值——那会让「只想试跑 2 台」变成真发 10 台。
```

`--limit 2` 的语义是「我只想拿 2 台机试试水」。如果用户手滑写成 `--limit=abc`，一个宽容的解析器会退回默认值 `Infinity`，然后**真的对 10 台机执行操作**。

用户的本意是「小心一点」，结果因为宽容变成了「全量执行」。这是最坏的一类失败。

未知参数也一样不放过——用一个 `consumed` 集合标记已消费的下标，剩下的就是没人认领的参数，直接报错并打印可用参数表。打错一个字母得到的是明确提示，而不是一次意料之外的全量运行。

> **规律：当默认行为比出错更危险时，就不该有默认行为。**

## 六、用页面自己的数字做断言

平台的批量文案弹窗规则是「**一行 = 一份**」。而我的文案是这样的：

```text
正文一行……

#tag1 #tag2 #tag3
```

正文、空行、标签行。直接粘进去——弹窗认为这是**两份**。10 台机需要 10 份，实际给了 20 份，于是机 1 拿到正文、机 2 拿到标签、机 3 拿到下一条的正文……**全线错位**。

而这个错位在页面上不显眼：每行都有内容，看起来填好了。

处理很简单，读取时压平成一行。但**只压平不够**——万一哪天这个逻辑失效了呢？所以填完之后立刻验：

```js
const m = (await capDlg.innerText()).match(/共\s*(\d+)\s*份/)
if (m && Number(m[1]) !== N) {
  throw new Error(`文案份数不符：弹窗显示 ${m[1]} 份，期望 ${N} 份（文案可能没压成一行）`)
}
```

弹窗自己会显示「共 N 份」。**页面上现成的数字，就是最好的断言。**

这条的价值在于它不依赖我对自己代码的信心，而是直接读系统的真实状态。只要弹窗还显示这个数字，断言就有效——反过来说，**措辞一变它就会静默失效**，这正是下一节要讲的问题。

## 七、断言结果，不要断言过程

流程里有个「目标应用检查」弹窗，我在代码里留了这么段注释：

```js
// 观察到三种情况：① 正常弹出→保存→关闭 ② 根本不弹，设备直接加好 ③ 弹了但点保存后按钮变灰不关。
// 所以这步是尽力而为，真正的成功判据是左侧「已选云手机（N）」。
```

三种情况，没有规律。硬等它出现会在情况 ② 卡死；假设它不出现会在情况 ① 被挡住。

处理方式是**放弃对这个弹窗的控制欲**：出现了就尽力点保存（点不到也无所谓），没关掉就兜底点 X，全程 `.catch(() => {})`。

然后**用一个与过程无关的结果指标来判定成功**——页面上的「已选云手机（N）」：

```js
const readSelected = () => page.evaluate(() => {
  const m = document.body.innerText.match(/已选云手机\s*[（(]\s*(\d+)\s*[)）]/)
  return m ? Number(m[1]) : -1
})
```

轮询读它，读到大于 0 才往下走。

> **别断言「我点对了按钮」，去断言「想要的状态达成了」。** 中间过程有几种分支不重要，重要的是结果。

同样的思路也用在等上传完成上：不是等某个 loading 消失，而是**连续两次采样数量不变**才算稳定——因为上传中途 DOM 里的条目数可能瞬时等于目标值（占位符先渲染出来），此时往下走就会传空文件。

### 后记：三天后，页面真的改版了

这篇写完第三天，平台改版了。

「批量上传视频」和「批量文案」原本各是一张独立卡片（`.fbp-card--file` / `.fbp-card--text`），改版后变成分批表格**列头上的一个「批量」小按钮**——两列共用同一个类名 `.fbp-col-batch`，只能靠 `title` 属性区分。同时我原来用来判断「是不是已切到分批模式」的那句文案，在新页面上**整个消失了**。

三处全断。适配花了 14 行：

```js
const candidates = [
  page.locator(`button.fbp-col-batch[title="${conf.title}"]`),   // ① 新版：按 title 区分
  page.locator(`${conf.oldCard} .fbp-card__btn`),                // ② 老版：旧卡片
  page.locator('.fbp-col-head').filter({ hasText: conf.colLabel }) // ③ 兜底：按列头文字
      .locator('.fbp-col-batch').first()
]
for (const btn of candidates) {
  if (await btn.count() > 0) { await btn.first().click(); return dialogByTitle(page, conf.title) }
}
throw new Error(`找不到「${conf.title}」的入口按钮，VMOS 页面可能又改版了`)
```

同理，「已切到分批模式」的判据也从**找一句文案**换成了**找表格元素在不在**——文案会被产品改，结构相对稳。

但真正让这次适配只花 14 行的，不是选择器写得多聪明，而是**它当初的失败方式是「报错停下」，不是「找不到就跳过」**。

设想另一种写法：找不到就 `if (btn) btn.click()` 静默跳过。那么改版当天，脚本会**一路跑到底**，打印出漂亮的 6 步进度，然后填出一张**没有视频、没有文案的空表**——而我要等到看截图时才发现，或者更糟，随手点了发布。

> 抗改版靠的不是选择器写得准，而是**选不中的时候会不会喊**。

### 改版顺带暴露了几处不会喊的地方

改版像一次突击检查，逼我把所有逻辑重新审视了一遍。连同上一节提到的「共 N 份」措辞依赖，一共**四处本该喊停却没有**。其中两处有对应的中止逻辑（文案份数、上传超时），只是判据留了后门；另外两处连中止都没有。

**第一处：上传等待的「瞎跑」放行。** 等待上传完成时，如果所有选择器都落空，`snap.count` 会返回 `-1`，而原来的判据里居然写着 `snap.count < 0` 也算通过。这意味着选择器全部失效时，脚本会认为「上传完成」，继续往下走。这属于那 25 处中止之一（超时逻辑），但判据过于宽容，给了静默放行一个后门。

**第二处：设备列表提前 break。** 设备列表是异步加载的，原来只要 `count() > 0` 就跳出循环，可能只加载出 2 台就继续了。这只是一个循环控制，根本没有配套的 `throw`。好在后面有 `deviceRows.length !== N` 兜底，所以它不会静默跑错，但会在半渲染时点「全选」只勾中一部分，然后被后面的检查拦下报错——制造了一个本可避免的假报错，徒增用户的困惑。

**第三处：表格填完只打印，不中止。** 填完表格后只是 `console.log` 有几行有视频、几行有文案，从不拦截。如果某次运行视频没传上去，脚本照样走到写进度、提示用户去点发布。这同样只是一个日志输出，没有任何中止逻辑。

共同点是**都没在该喊的地方喊**——前两处要么放行、要么把问题甩给下游，第三处干脆一声不吭。这几处修完之前，那 25 处主动中止是有缺口的。尤其是第三处，由于中止发生在写进度文件之前，一旦加上 `throw`，进度就不会前进，用户直接重跑即可——但现在，它连喊都不会喊。

值得一提的是截图逻辑。脚本本来就会在关键步骤截图，例如 `result-screenshots/round002-1785731627404.png`（带轮次号）。修复方案不是新增截图，而是**复用已有的截图逻辑，把它挪到 `throw` 之前**，确保中止时必有现场证据。

## 八、它绝不点「发布」

整个脚本跑完，最后打印的是：

```text
══════════════════════════════════════════
  表单已填好，脚本不会点「发布」。
  请人工核对后自行点击右下角「发布」。
  这轮没发想重来：bash publish.sh --redo
══════════════════════════════════════════
```

技术上加一行 `click('发布')` 完全做得到。不加的理由：

**在点「发布」之前，所有操作都是可撤销的——关掉页面，什么都没发生。点下去的那一刻，10 条内容进入 10 个真实账号，公开可见，撤不回来。**

前面写了那么多校验，本质都在降低「填错」的概率。但概率降不到零：平台可能改版，网络可能抽风，可能有我没预料到的第四种弹窗情况。所以在最后留一道**人的确认**——**这道防线不依赖我把所有情况都想到。**

这个设计还换来一个很实际的好处：**因为不发布，所以可以随便跑。** `--redo` 敢写、`--limit 2` 敢试、跑错了关掉页面重来就行。

反过来说，一个「会自己发布」的脚本，每次运行就是一次赌博，你会**不敢测它**——而不敢测的工具会烂得更快。

同样的道理体现在 `--dry`（只打印本轮清单）和 `--plan`（打印整体排期）上：这两个参数在 shell 层就被拦截，根本不启动浏览器。所以文档里能写「随便运行，不会有任何影响」。**给用户一个绝对安全的探索入口，他才会真的去用这个工具。**

## 九、清点一下这 630 行

回头数了下脚本里的 `throw new Error`（21 处）和 `process.exit(1)`（4 处）——合计 25 处主动中止。将其按类别归并如下：

| 检查 | 防的是什么 |
| --- | --- |
| 参数值非法 / 未知参数 | 试跑 2 台变成真发 10 台 |
| 进度文件丢失但编号表在 | 整批重发已发过的内容 |
| 视频文件缺失 | 编号错位，全盘错乱 |
| 可用视频 < 每轮台数 | 同一轮内出现重复 |
| 未登录 / 设备列表为空 | 在错误的页面上瞎点 |
| 勾中数 ≠ `--limit` | 误发给多余的机器 |
| 「已选云手机」读不到或为 0 | 设备根本没加进去 |
| 找不到关键控件 | 页面改版，后续全是盲操作 |
| 设备数 ≠ 本轮条数 | 必填项缺失导致发布失败 |
| **设备顺序变化** | 破坏账号内不重复的保证 |
| 上传失败 / 超时 | 传了空文件（有缺口，见后记） |
| **文案份数 ≠ 期望** | 文案全线错位 |

真正在「操作页面」的代码——点按钮、填输入框、传文件——撑死 150 行。剩下的全在回答同一个问题：**怎么确保它没在悄悄干错事。**

这个比例不是过度设计。因为一个 630 行的脚本里有 25 个地方选择停下来，本身就说明了问题的严重性。这个脚本的失败模式**不是「报错停下」**，而是**「跑得很顺利，然后 10 个账号发了重复内容」**。前者立刻可见，后者没有任何提示。

**当失败是静默的，防御就必须是显式的。**

## 十、可靠性有一半在 README 里

最后一件出乎我意料的事：使用说明写了 305 行，比核心逻辑还长。

因为实际使用者不写代码。「cd 到目录」对他们不是一个已知概念，所以文档里得写「输入 `cd ` 然后把文件夹**直接拖进终端窗口**」。

但真正重要的是「**千万别做的事**」那一节，四条，每条都写了后果：

> 1. 别删编号表和进度文件——**会导致重复发布已经发过的视频**
> 2. 别给视频改名或删除——文件名就是编号，改了会让整套编号错乱
> 3. **别在两台电脑上同时用**——进度存在本机，两个人各跑各的会重复发布
> 4. 别手动改进度里的数字——想重跑上一轮用 `--redo`

第 3 条是代码解决不了的。进度存在本地文件里，天然不支持多机协作。可以上云、可以加锁，但对一个内部工具来说，**写进文档、约定「只由一个人跑」是更合适的成本**。

识别出哪些问题该用代码解决、哪些该用约定解决，本身就是设计的一部分。

另外还配了张错误对照表，把每个 `throw` 的文案映射成「人该做什么」：

| 错误里出现 | 意思 | 怎么办 |
| --- | --- | --- |
| `未登录` | 登录过期了 | 重新登录一次再跑 |
| `设备顺序变化` | 云机顺序变了 | **别自己改**，找技术同事 |
| `等待上传超时` | 网络慢或云盘满了 | 检查网络；清理云盘 |

这张表能存在的前提是：**每个报错信息都足够独特、能被搜到**。写 `throw new Error('失败')` 就做不成这件事。

## 十一、一句话总结

一个取模运算解决了排期，把整个系统的状态压缩成一个整数；剩下数百行代码都在校验这个公式的前提有没有被破坏。

**如果一个系统的失败是静默的，那它的正确性就不能靠「跑起来没报错」来证明。** 你得主动去检查那些让它成立的假设——并且在假设被打破的那一刻，**停下来，而不是继续跑。**

一个 630 行的脚本里有 25 个地方选择停下来，这不是胆小，而是负责。
