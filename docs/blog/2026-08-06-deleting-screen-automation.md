# 把 1500 行自动化删掉——像素阈值里藏着一台特定的屏幕

> 从 13 寸换到 16 寸，脚本开始选不中文件，却又报「已上传成功」。修好它需要给每台电脑重新标定一次阈值；而这个工具要给多位同事用。最后我删掉了整套自动化，只留下人做会悄悄做错的那部分。

## 一、同一个问题，两种界面

上一篇写的是 VMOS 那套批量发布脚本：10 台云手机、205 条视频、一个取模运算解决排期。这篇是它的姊妹项目——同样的排期逻辑，换到 **GeeLark** 上。

排期部分几乎原样搬了过来：

```python
# 第 r 轮，第 d 台机（d 从 0 数）→ 视频 [(r-1+d) mod N]，10 台共用文案 r
# 轮1: 机1→v1  机2→v2  …  机10→v10   文案 001
# 轮2: 机1→v2  机2→v3  …  机10→v11   文案 002
# 总轮数 = min(视频数, 文案数)
```

（和上一篇里的 `(r-1+d-1) % N` 是同一条规则，只是那边的 `d` 从 1 数起。）

真正不一样的是**怎么把结果送进平台**。

VMOS 是网页，Playwright 能拿到 DOM，可以按 class 找按钮、读弹窗里的「共 N 份」当断言。GeeLark 是 **Electron 桌面客户端**，而且：

- **屏蔽了 CDP 调试端口** —— 没法像浏览器那样接进去查 DOM；
- **内部按钮对 macOS Accessibility API 不可见** —— AppleScript 遍历 `UI elements` 只能看到一个空壳窗口。

两条路都堵死之后，只剩下最后一条：**截屏，然后认屏幕上的像素颜色。**

## 二、像素方案长什么样

它并不是随手写的。为了在没有任何结构信息的情况下判断界面状态，我给每一步都标定了一条颜色判据。比如判断「表格编辑弹窗开没开」：

```python
def table_modal_open():
    """判据是弹窗里那个蓝色的「点击上传」按钮——它固定在窗口中偏左，
    而正常页面这块区域没有任何蓝色元素（页面上的蓝色是右上角「添加」、
    右侧「获取」、左下角「发布」，都在判据区之外）。实测弹窗开着时
    这里有 700+ 个蓝色像素，没开则是 0。
    """
    return find_blue_button(screenshot(), wr(0.28, 0.22, 0.48, 0.42)) is not None
```

注意 `wr(0.28, 0.22, 0.48, 0.42)`——所有区域都用**相对比例**写，而不是绝对坐标。当时我以为这就解决了「换电脑」的问题。

最关键的一步是「在文件对话框里全选 10 个视频」。这一步没有任何可读的状态，于是判据变成了：

```python
def screen_blue_ratio():
    """全屏截图里「选中高亮蓝」像素的占比。

    文件对话框里被选中的文件是整行系统蓝填充，选中 10 个会占到全屏的 10% 以上，
    没选中只有 1% 左右（实测 12.4% vs 1.5%）。GeeLark 自己的蓝色按钮也会被算进
    去，所以只看绝对值不准，要看操作前后的差值。
    """
```

然后是三种按键策略挨个试，谁能把蓝色比例拉高 2 个百分点就算成功：

```python
strategies = [
    ("右箭头进列 + Cmd+A", ...),
    ("直接 Cmd+A", ...),
    ("下箭头选首项 + Cmd+A", ...),
]
for name, action in strategies:
    before = screen_blue_ratio()
    action()
    after = screen_blue_ratio()
    if after - before > 0.02:
        print(f"  已选中文件（{name}，蓝色高亮 +{(after-before)*100:.1f}%）")
        return True
```

**这套东西是能跑的。** 在我的 13 寸上，第一种策略一次就中，实测 +3.3%。整个流程从新建任务到填完表格，六步全自动，我拿它跑了很多轮。

## 三、换台电脑就废了

换到 16 寸 M3 之后，同一步开始失败：蓝色高亮只涨了零点几个百分点，三种策略全部落空。

原因很朴素，但我当时没往这想：

**判据是「占整个屏幕的比例」，而文件对话框的物理大小是固定的。**

屏幕越大，分母越大，同样选中 10 个文件，那片蓝占全屏的比例就越小。13 寸上是 12.4%，换到更大的屏幕上可能只有 7%、5%。而 `> 0.02` 这个阈值，是在 13 寸上量出来的。

我以为用相对比例写区域（`wr(0.28, 0.22, ...)`）就等于「屏幕无关」。**区域确实跟着屏幕缩放了，但阈值没有。** 那个 `0.02` 是一个用实测标定出来的经验值，它里面编码的不是「选中了文件」这个事实，而是「在那台 13 寸上选中文件时会发生什么」。

> **一个标定出来的常数，本质上是把当时的环境固化进了代码。** 它不会告诉你它依赖什么，也不会在环境变了的时候提醒你——它只是开始给出错误答案。

这类隐式依赖很难被发现，因为**代码里看不出来**。`0.02` 旁边没有任何东西写着「本值只在我那台 13 寸上量过」。

## 四、真正糟糕的是：失败被报成了成功

如果它只是失败，事情还好办——报个错停下来，我当场就知道要修什么。

实际发生的是：

1. 文件没选中；
2. 脚本继续往下走，在**没选中任何文件的情况下**点了「打开」；
3. 上传区域空空如也；
4. 然后 `upload_done()` 返回了 `True`。

```python
def upload_done():
    """视频是否已上传完成。

    两个互相独立的视觉信号，任一成立即可：
      1. 步骤条第 3 步「编辑内容」的圆圈变蓝（上传完会自动跳到第 3 步）
      2. 预览区出现绿色进度条 / 绿色对勾
    """
```

注释里写着「两个**互相独立**的视觉信号」。这句话是错的，而且错得很典型。

这两个信号在**语义上**独立（一个看步骤条、一个看预览区），但在**失效模式上**完全不独立——它们都建立在同一个前提上：*屏幕上某个相对区域里的颜色，能反映界面的真实状态*。这个前提一旦因为屏幕尺寸而崩塌，两个信号会**一起**给出错误答案。

> **冗余判据只有在失效模式独立时才叫冗余。** 两个都靠「读屏幕像素」的检查，不是双保险，是同一个保险按了两次。

于是就有了最坏的那种结局：脚本一路跑到底，打印出漂亮的六步进度，填好一张**没有视频的表**，然后提示我去点发布。白发一轮，还不知道。

上一篇里我写过一句：「这个脚本的失败模式不是『报错停下』，而是『跑得很顺利，然后 10 个账号发了重复内容』」。这次是同一句话的另一个版本——只不过这回，静默出错的不是业务逻辑，是**我用来检查业务逻辑的那套眼睛**。

## 五、能修，但值不值得

修的办法是有的：每台电脑第一次用的时候跑一次标定，量出「选中/未选中」两种状态下的实际比例，把阈值写进配置。

我认真算了一下这条路的成本：

| | 代价 |
| --- | --- |
| 标定流程 | 得写一个引导程序，让人手动选一次文件、再取消选一次 |
| 使用者 | 非技术同事，屏幕各不相同（13 寸、16 寸、外接显示器） |
| 触发条件 | 换电脑要重标，接外接显示器要重标，甚至改个缩放比例都可能要重标 |
| 失败后果 | 还是「静默发错」，只是概率低一点 |

最后一行是压垮它的那条。**一个需要正确标定才安全的工具，交到不知道「标定」是什么的人手上，风险不会因为多了一道流程而消失。**

所以我换了个问题：不问「怎么修好这套自动化」，而是问——

**这个脚本里，哪些部分是人做不了的？**

| 步骤 | 人来做 | 出错会怎样 |
| --- | --- | --- |
| 算出第 87 轮该给第 3 号机发哪条视频 | 要维护 Excel、算取模 | **错一格就重复发布，当场看不出来** |
| 把 10 个视频挑出来、改成统一命名 | 一个个找、一个个改名 | 名字对不上，GeeLark 匹配不到 |
| 填 10 行表格（序号/视频名/文案/时间） | 手打，来回复制粘贴 | 错行、错位 |
| 在文件框里按 Cmd+A 全选 | **三秒** | 看得见，选没选中一眼就知道 |
| 点几个按钮 | **十几秒** | 看得见 |

分界线非常清楚：**上面三行是「人做会悄悄做错」，下面两行是「人做几秒钟，而且错了立刻看得见」。**

自动化的价值从来不是「覆盖的步骤多」，而是「**替人扛住那些他扛不住的部分**」。而我当初花最多力气去攻的，恰恰是最不值得自动化的那一半——因为它难，所以看起来重要。

## 六、方案改了三轮，最后是删得最狠的那个

砍掉自动化这件事，我做了三次才做对：

**第一轮：`--manual-pick`。** 脚本跑到选文件那步停下来，打印「请手动选中 10 个文件，选好后回车继续」，人选完按回车，脚本接着自动跑后面几步。

看起来很合理：保留了大部分自动化，只把不可靠的一步交给人。

**第二轮：被否掉。** 「回车继续」对非技术使用者是负担——她得盯着终端和 GeeLark 两个窗口来回切，还得知道什么时候该切回来。而且脚本后面那几步**依然用着同一套像素判据**，同样会误报。留一半自动化 = 留一半误报。

**第三轮：完全不碰 GeeLark。** 脚本变成两秒钟结束的本地准备：

```text
══════════════════════════════════════════════════════════════
  素材已备好，接下来在 GeeLark 里操作：

  ① 批量上传视频 → 本地上传，选下面这个文件夹里的 10 个视频
     /Users/xxx/Downloads/geelark-tiktok-skill/本轮视频

  ② 表格编辑 → 点击上传，选这个文件
     /Users/xxx/Downloads/geelark-tiktok-skill/template_filled.xlsx

  在 GeeLark 的文件框里按 Command+Shift+G，粘贴路径即可跳过去
  （①的路径已复制到剪贴板）
══════════════════════════════════════════════════════════════
```

算排期、拷 10 个视频到 `本轮视频/` 并改名 `v01`~`v10`、用 openpyxl 生成填好的 Excel、打印两个路径。**完。**

中间我还想过第四种：加个 `--auto` 开关，谁的屏幕标定过谁就用自动模式。也否了。**两条代码路径意味着两倍的维护，而使用者根本没有能力判断自己该用哪条**——她只会用文档里写的那条，那另一条存在的意义就只剩下「有一天有人误开了它」。

> **给非技术用户的工具，只能有一条路。** 开关是给知道自己在干什么的人准备的。

## 七、删掉之后，一串问题跟着消失了

这是我没预料到的部分。砍掉自动化之后，一批看似无关的麻烦自动没了：

**依赖从 3 个减到 1 个。** 原来需要 `pyobjc-framework-Quartz`（模拟点击）+ `Pillow`（读像素）+ `openpyxl`（写 Excel），现在只剩最后一个。

这不是洁癖。同事装依赖时卡住了，报错是 `Cannot locate a working compiler`——因为 pyobjc 在 macOS 系统自带的 Python 3.9 上没有预编译包，得现场编译，而她机器上没有完整的编译工具链。**一个已经不再被调用的功能，却成了整个工具跑不起来的前提。**

改法是把这两个包降级成可选导入：

```python
# 当前流程只做本地准备（算排期 / 拷视频 / 生成 Excel），唯一必需的是 openpyxl。
# Quartz 和 Pillow 只被下半个文件里那套已停用的 GeeLark 自动化代码用到，
# 所以缺了不退出、只置空——真去调用才会报错。
try:
    from Quartz import (...)
except ImportError:
    CGEventCreateMouseEvent = None
```

**不再需要任何系统权限。** 原来要「屏幕录制」（截屏）和「辅助功能」（模拟点击）两项授权。这两项在 macOS 上都需要重启终端才生效，而且**没给权限时 screencapture 不报错，只是拍出一张空壳画面**——脚本会以为自己看见了屏幕，实际上是瞎的。这个坑我当时甚至专门写了段代码去检测它：

```python
if avg > 250 or avg < 5:
    print("    ⚠ 画面几乎纯白/纯黑，多半是没给终端「屏幕录制」权限，脚本其实是瞎的")
```

现在这段检测跟着自动化一起进了「不再被调用」的那一半——**它防的那个问题已经不存在了，因为脚本根本不截屏。最好的错误处理是让那个错误不可能发生。**

**产物位置也顺手改了。** 早期临时目录放在家目录（为了让「前往文件夹」少打几个字，那是自动化时代的优化）。现在改成放在脚本目录下、和 `template_filled.xlsx` **并排**：

```text
geelark-tiktok-skill/
├── 本轮视频/                ← ① 上传这里面的 10 个视频
│   ├── v01.mp4 ~ v10.mp4
└── template_filled.xlsx     ← ② 表格编辑选这个
```

两样东西在同一个文件夹里，对着访达一眼能找到。**当操作者从脚本变成人，「方便」的定义也跟着变了。**

## 八、两个为非技术用户做的减法

删自动化的过程中，还砍掉了两个我自以为贴心的功能。

**砍掉输出里的 shell 命令。** 脚本原本会打印一行 `echo -n '路径' | pbcopy` 供人复制路径。被指出这是噪音——**非技术的人看到命令行，会以为自己还得敲一遍。** 现在改成脚本内部直接调 `pbcopy`，输出里只留一句「①的路径已复制到剪贴板」。

**砍掉自动弹访达。** 原本跑完会自动打开访达定位到视频目录，想法是「让她直接拖进 GeeLark」。后来发现：

```python
# 不自动打开访达：GeeLark 的上传框不接受拖拽，只能在框里自己选文件，
# 弹个访达出来反而让人误以为那就是上传界面。只打印路径。
```

**一个基于错误假设的便利功能，比没有这个功能更糟**——它会把人引向一条走不通的路，而人不会怀疑工具，只会怀疑自己。

## 九、代码删了，但没删干净（故意的）

`publish.py` 现在有 1967 行，其中**大约四分之三是已经不再被任何地方调用的自动化代码**：`setup_window`、`click`、`screenshot`、`select_all_in_dialog`、`step_upload_videos`…… 全部保留。

按常理这些该删掉——死代码是负债。但我留下了，理由是**那些函数里的注释是这个项目最贵的部分**：

```python
# 必须用 key code 5 而不是 keystroke "g"：修饰键一旦丢失就变成单敲一个 g，
# 在文件对话框里会触发首字母跳转，随后的回车会把跳到的那个文件直接打开
```

```python
# 原来还有第四种「Tab 换焦点 + Cmd+A」，已删除：它紧跟在 Cmd+A 之后发
# Tab，一旦 Command 没松干净就变成 Cmd+Tab，弹出应用切换器把整个流程带偏
```

```python
# 人只要中途切去别的窗口（比如去看聊天），后面所有像素判断测的就都是
# 别人的画面——蓝色高亮恒为 0。这正是长期「时好时坏」的主因
```

这些是几十次失败换来的，而且**每一条都不可能靠读文档得知**。删掉函数，这些知识就一起没了；哪天要重做自动化（比如 GeeLark 哪天开放了调试端口），得从零再踩一遍。

我在文档里明确写了它的状态，免得后来人以为是漏删：

> **原自动化代码仍保留在 `publish.py` 下半部分**（未被调用），内含大量踩坑注释，日后若要重做自动化可作参考

> **区分「死代码」和「归档的经验」。** 前者该删，后者该标注清楚再留着。判断标准是：删掉它，是否会丢失无法重新推导出来的信息。

## 十、剩下的那部分，防御一条没少

自动化没了，但「防静默出错」的那套东西全部留着，因为**排期逻辑的失败方式还是老样子——不报错，只是悄悄发重复内容**：

| 检查 | 防的是什么 |
| --- | --- |
| `progress.json` 只在整轮成功后才写 | 中途失败导致进度错乱 |
| 视频不足 10 个直接中止 | 同一轮内出现重复 |
| `config.json` 缺失/格式错 → 明确报错 | 文案填到不存在的设备上 |
| `--round` 指定轮次**不写进度** | 补发/测试污染正式进度 |
| `--new-cycle` 不加 `--yes` 只预览 | 误操作把进度归零 |
| 换素材时旧进度备份成 `.bak` | 改错了能找回 |

其中一条值得单独说。`--dry` 模式下，我强制把云机序号打出来让人核对：

```python
# 云机序号填错是最隐蔽的故障：整轮都会跑成功，只有文案悄悄落到
# 不存在的设备上。所以每次 --dry 都把当前配置摆出来让人核对。
print(f"  云机序号（config.json）: {', '.join(PHONE_IDS)}")
print("  ⚠ 不一致的话脚本照样跑完，但文案会填到不存在的设备上，白发一轮。")
```

这是个**代码无法验证**的东西——脚本没法知道你 GeeLark 账号里那几台机的序号是多少。既然验不了，就**把它摆到人眼前**，并且写清楚错了会怎样。

上一篇里那条「哪些问题该用代码解决、哪些该用约定解决」，这里又碰到一次。

## 十一、一句话总结

判据里那个 `0.02`，把一台 13 寸屏幕悄悄编码进了代码。换台电脑，它不报错，只是开始说谎——而且和它一起说谎的，是本该用来交叉验证它的另一个判据。

**当你的检查机制和被检查的对象共享同一个失效前提，那不叫检查。**

最后的选择不是把它修好，是把它删掉：留下人做会悄悄做错的部分（排期、命名、填表），把人做几秒钟且错了立刻看得见的部分（点几下鼠标）还给人。

**一个脚本的价值不取决于它替你做了多少步，而取决于它替你扛住了哪些你扛不住的错误。** 删掉那 1500 行之后，工具第一次做到了「谁的电脑上都能跑，而且不会悄悄发错」。
